StudyPythonTypeScriptS3

Does Supabase Storage keep S3's conditional-write promises?

Supabase's S3 endpoint ignored If-None-Match, so concurrent "create-once" calls all succeeded. I built master and a community fix from source, ran a 53-case conformance matrix on two storage backends, and checked create-once under container, Postgres and network faults. With 32 clients racing for one key, 32 won on master and exactly 1 with the fix. The fix still leaves If-Match (compare-and-swap) ignored, and my write-up says so.

Code and results Issue #1635 Review of the fix, #1636 Draft PR #1712: 8 regression tests

Open sourceGoMCPPR open

SigNoz MCP server: a tool answer too big for AI clients

A tool that lists a service's slowest operations returned 115,526 characters for a busy service, more than Claude Code accepts in one tool result. My pull request adds an optional limit (default 50) and a note saying how many rows were omitted. The same call now returns 5,882 characters, and the full table is one parameter away. The issue's author approved it; it is waiting for a maintainer (open as of 19 November 2026).

LibraryPythonPyPI

s3lin

A linearizability checker for S3 conditional-write histories, packaged as a typed library with no runtime dependencies. It names the key and the operation where a history stops making sense. On 54 recorded histories (288,820 operations) it agrees with my original checker on all 1,245 keys. Version 0.1.0, so brand new.

PyPI GitHub

StudyPythonSimulation

LLM router recovery simulator

A trace-driven simulator of LLM request routing: 8 vLLM-like replicas, public Mooncake traces, 10 policies modelled on SGLang, llm-d, Dynamo and LMetric, 10 seeds. My recovery-aware router recovered from a 30-second replica failure in 9 of 9 held-out seeds on both traces; variants without its recompute budget drifted into a 13 to 19 s p99 state at 95% load, against 3.8 to 5.5 s with it. It is not faster than SGLang's policy at recovery (165 s vs 125 s median on one trace).

Write-up on request. Simulation, not production.

NineLives: an on-call agent with durable memory

Recalls similar past incidents by vector search (12 of 12 correct on benchmark cases) and runs only allowlisted fixes. Memory lives on a 3-node CockroachDB cluster, written in the same transaction as each fix, and it kept serving through live node kills (0.11 s and 6.85 s pauses). An ablation showed the memory is load-bearing.
